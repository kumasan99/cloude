# 運用体制 — クロ（COO）とCEOの週次サイクル

ダッシュボードは「作って終わり」ではなく、**回して初めて価値が出ます**。
以下は最小の運用サイクルです。慣れるまでは週1回・15分で十分です。

---

## 週次サイクル（推奨: 月曜の朝）

```
① CEO: 資料を置く（5分）
    data/inbox/ に、先週更新された資料を上書き・追加するだけ
              ↓
② クロ: レポート生成（3〜5分・自動）
    ダッシュボードで「レポートを更新」を押す
              ↓
③ CEO: 判断する（10分）
    「あなたの判断が必要なもの」を上から順に 承認 / 却下 / 保留
              ↓
④ クロ: 次に必要な資料を提示
    「クロが待っている資料」に反映される → 翌週の①に戻る
```

### 各ステップの中身

**① 資料を置く**
- 毎週すべてを更新する必要はありません。更新があったものだけで構いません。
- 何を置けばいいか迷ったら、ダッシュボードの「クロが待っている資料」の未チェック項目から。

**② レポート生成**
- ダッシュボード右上の「レポートを更新」ボタン。
- 生成されたレポートは `reports/report-YYYY-MM-DD-HHMM.json` に保存され、
  過去分はヘッダーのプルダウンからいつでも見返せます。

**③ 判断する**
- 「あなたの判断が必要なもの」には、**CEOにしか決められないこと**だけが上がります。
- 各カードには必ず「選択肢」と「クロの推奨」が付いています。
  推奨に乗るなら承認、違う考えなら却下してメモに理由を残してください。
  **その理由が次回以降の報告の精度を上げます。**
- 決裁は `reports/decision_log.json` に記録され、いつ何を決めたかが残ります。

**④ 次の資料**
- レポートの「今回足りなかったもの」がそのまま翌週の宿題になります。

---

## 月次でやること

- **KPIの目標値を入れる** — `config/kpi.yaml` の `target` を埋める。
  目標が入ると、クロの評価が「所感」から「達成/未達」に変わります。
- **決裁ログを振り返る** — 保留のまま放置されている判断が無いか確認。
- **改善提案の進捗を確認** — 前月の improvements のうち、何が実行されたか。

## 設定ファイル

| ファイル | 役割 | いつ触るか |
|---|---|---|
| `config/company.yaml` | 会社の前提、CEOの関心事、決裁範囲 | 最初に1回。方針が変わったとき |
| `config/kpi.yaml` | 見たいKPIと目標値 | 月次で目標を更新 |
| `config/data_requirements.yaml` | 必要資料のチェックリスト | 業種特有の資料を足したいとき |

**`config/company.yaml` の `ceo.priorities` は特に重要です。**
ここに書いたことが、クロの報告の切り口を決めます。
「資金繰り」と書けば資金繰り中心に、「属人化の解消」と書けば組織の話が増えます。

**`ceo.decision_scope`** に書いた範囲が、「あなたの判断が必要なもの」に上がる基準になります。
判断カードが多すぎる / 少なすぎると感じたら、まずここを調整してください。

---

## よくある詰まり方

| 症状 | 原因 | 対処 |
|---|---|---|
| KPIが「不明」ばかり | 財務資料が無い | `data/inbox/finance/` に試算表を置く |
| 判断カードが上がってこない | 資料が少なく、判断材料が無い | 優先度Aの資料を追加する |
| 判断カードが多すぎる | `decision_scope` が広すぎる | `config/company.yaml` で範囲を絞る |
| 数字が実感と違う | 出典の資料が古い / 一部だけ | レポートの「出典」欄で元ファイルを確認 |
| 報告が一般論に見える | 会社の前提が空欄 | `config/company.yaml` を埋める |

## 自動化（任意）

毎週手で押すのが面倒になったら、`POST /api/dashboard/generate` を叩くだけなので
cron やタスクスケジューラで自動化できます。

```bash
# 毎週月曜 7:00 にレポートを生成
0 7 * * 1 curl -s -X POST http://localhost:8000/api/dashboard/generate -H 'Content-Type: application/json' -d '{}'
```

ただし**最初の1〜2ヶ月は手動で回すことをおすすめします。**
報告の粒度が自社に合っているかを確かめてから自動化したほうが、結果的に早いです。

## MF月次スナップショット運用（2026-08-22開始・全社クロ統一方式）

グループ全社がMFクラウド会計を利用しているため、取得はクロに一本化する。
接続は1事業者ずつのため、月1回の「切替週間」で全社を巡回する。

### 月次の巡回手順（月次締め後）
1. ワンダー（常時接続）: クロが取得 → スナップショット書き出し
2. 社長がMF接続を再認可でパートナーズに切替 → クロが取得・書き出し → 完了を報告
3. 同様に COCO → HD の順で切替（各5分。全体でも社長の作業は15分以内）
4. 最後にワンダーへ戻して常時接続に復帰

マネーフォワード クラウド会計から取得した月次PL・BSを、Driveの
`01_data/finance/MF月次スナップショット/` に書き出す。

- ファイル名: `ReSow_W_月次PL_YYYY_取得YYYYMMDD` 形式（取得日を必ず入れる）
- 目的: ①MF接続（ベータ）が使えないときの控え ②野原さん・経理マネージャー・松下さんとの数字共有 ③履歴の保存（MFはライブのため過去時点の姿が残らない）
- 更新: クロが月次締め後（または隔週）に取得・書き出し。古いスナップショットは残す（上書きしない）
- 正の優先順位: 現金残高は資金繰り表（通帳ベース）が正。損益はMFが正

### スナップショット時の整合性チェック（毎回実施）
クロは書き出しのたびに以下を突合し、差異があればレポートに明記する。
1. MFの売上 vs 事業所別売上シート（国保連請求ベース）
2. MFの現預金 vs 資金繰り表（通帳ベース）※現金は資金繰り表が正
3. 会社間取引の残高（売掛/買掛/貸付/借入）が法人間で対称か
4. 前回スナップショットからの遡及修正の有無（修正があれば履歴として記録）
